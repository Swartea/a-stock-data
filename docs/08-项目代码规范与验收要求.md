# 大A数据项目代码规范与验收要求

版本：1.0  
制定日期：2026-09-11  
适用范围：`analysis/`、`scripts/`、`tests/` 及相关配置、流程图、报告生成链路。

## 1. 目标与执行原则

保证数据含义准确、失败状态可信、计算可验证、报告可追溯、代码可维护。

- **必须**：新增代码及本次修改涉及的代码应满足；不满足时不得宣称完成验收。
- **建议**：默认采用；不采用时在变更说明中写明原因。
- 本规范描述目标要求，不表示现有项目已经满足。历史问题按第 12 节分阶段整改，不要求一次性重写。
- 不得为了通过测试修改既定业务口径。业务口径存在歧义时，应先明确规则、示例和边界，再修改实现。
- 避免与任务无关的大规模格式调整、重命名或架构迁移。

## 2. 模块与依赖边界

主调用方向应为：入口编排 → 数据采集 → 数据校验 → 分析计算 → 报告模型 → 渲染与产物管理。

| 职责 | 必须遵守的边界 |
| --- | --- |
| 入口与编排 | 解析参数、组织阶段、处理总状态；不得堆积计算公式和报告正文 |
| 数据采集 | 负责请求、解析、单位转换和来源记录；不得生成交易结论或写报告 |
| 分析计算 | 接收明确输入并返回结果；核心计算不得隐式联网或读取当日报告 |
| 报告模型 | 汇总结论、风险、表格和来源；供不同格式共用 |
| 渲染器 | 负责格式展示；不得重新计算评分、价位或修改分析结果 |
| 产物管理 | 负责路径、写入、状态和文件检查；不得把部分成功报告为完整成功 |

具体目录可渐进调整，不强制立即迁移。新增大块功能不得继续直接堆入主分析器。

- 禁止通过全局替换 `requests.get`、其他模块函数等方式改变运行行为。
- 运行计时、来源状态等必须归属于本次运行上下文，避免共享可变全局状态。
- 建立可安装的包结构后使用标准导入；历史 `sys.path` 补丁逐步移除，新增业务模块不得继续复制此模式。
- 多职责函数、重复分支优先拆分；文件行数作为评审信号，不作为机械验收指标。

## 3. 命名、类型与注释

- 函数、变量使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`。
- 公共函数必须标明参数和返回类型；跨模块数据使用 `TypedDict`、`dataclass` 或等价模型约束。
- 金额、比例、日期字段应明确单位或口径，例如 `market_cap_yuan`、`change_pct`、`trade_date`。
- 百分数统一约定：`change_pct=5.0` 表示 5%；小数比例使用 `_ratio`，不得无说明混用。
- 核心公式的注释必须说明业务含义、输入口径、边界条件和缺失处理。
- 注释与实现同步更新；禁止保留“最近”实际取极值、“并行”实际串行等矛盾描述。
- 任务编号、临时排障过程、提交历史应移入文档；代码仅保留理解当前行为所需的背景。
- 禁止静默使用 `default=str` 掩盖未定义的序列化类型；应显式转换日期、数值和模型。

## 4. 数据返回契约

采集层应统一返回结构。迁移期可通过适配器兼容旧接口，避免一次性破坏所有调用方。

```json
{
  "status": "ok",
  "data": {"rows": []},
  "source": "provider.endpoint",
  "as_of": "2026-09-11",
  "fetched_at": "2026-09-11T16:00:00+08:00",
  "scope": "stock",
  "units": {"amount": "CNY"},
  "error": null
}
```

上例展示结构，实际 `ok` 数据必须满足对应端点的有效性规则；空记录集通常应标为 `empty`。

| 状态 | 定义 | 报告展示 |
| --- | --- | --- |
| `ok` | 获取成功且通过字段、类型、口径校验 | 正常展示 |
| `empty` | 请求及解析成功，业务确认无记录 | 显示“该期间无记录”等具体原因 |
| `error` | 网络、解析或校验失败 | 显示数据获取失败及影响 |
| `unsupported` | 数据源或标的不支持此能力 | 显示不适用或不支持 |

- 不得混用 `None`、空字典、错误字典表达同一种状态。
- 返回错误对象不等于成功；调用方必须检查状态，而非只检查是否抛异常。
- 上游结构变化、缺字段不能自动解释为“无记录”。
- `error` 必须包含稳定错误码、可读消息及 `retryable`；不得包含密钥或完整敏感响应。
- `as_of` 表示数据实际时点，`fetched_at` 表示采集时间；未知时点使用 `null`，不得用今天代替。
- 价格必须记录复权方式；资金指标必须明确个股、行业或全市场范围。
- 新增字段必须给出类型、单位、缺失含义和样例；破坏兼容时更新 `schema_version` 并提供迁移方式。

## 5. 网络、超时与重试

- 每次请求必须设置连接与读取超时；整项采集任务还必须有总耗时预算。
- “时间盒”必须有实际执行上限。仅限制重试次数或声明未使用的 `timeout` 参数不符合要求。
- 重试只用于可恢复错误；参数错误、明确不支持和成功空结果不得反复重试。
- 使用有上限的退避与抖动；最后一次失败后不再无意义等待。
- 内外层重试必须统一预算，禁止重试次数相乘且无法预测耗时。
- 并发必须有数量上限，同一服务共享限流。使用全局会话的客户端须先确认并发安全。
- 保持 TLS 证书校验开启；不得将 `verify=False` 作为生产默认或自动兜底。
- SSL EOF、证书验证错误、HTTP 风控、业务空结果必须分别记录，不得无证据归为同一根因。
- 备用源切换必须记录实际来源、切换原因和口径差异。缓存必须标明数据日期与有效期，不得伪装成实时数据。

## 6. 计算与数据质量

- 核心计算应为确定性函数；相同输入和规则版本产生相同结果。
- 不得将缺失值当作零、正常或中性信号，除非业务规则明确允许并披露影响。
- 评分必须记录参与指标、缺失指标、权重及规则版本。缺失数据如何影响得分必须有明确规则。
- 最近支撑：默认取不高于现价的最大有效候选；最近压力：默认取不低于现价的最小有效候选。
- 若产品选择区间极值或允许跨越现价，必须另行命名并说明规则，不能继续称作最近支撑/压力。
- 无有效候选时返回缺失及原因，不得为了填满报告生成无依据价位。
- 同一计算中必须统一日期、币种、比例单位和复权口径，避免实时价与不兼容历史价格直接比较。
- 数据新鲜度应结合交易日历、盘中/盘后及源更新时间判断，不得只用星期数判断节假日。
- K 线新鲜度、价格有效性等关键检查必须在依赖它们的结论发布前执行；失败后的中止或降级策略必须明确。
- 回溯分析须使用当时可获得的数据，不得隐式使用未来财报或当前行业分类。

## 7. 报告与产物

- MD、HTML、DOCX、PDF 必须共用已计算的结论与数据口径；渲染层不得各自维护一套评分公式。
- 报告首页必须展示分析时点、关键缺失数据及其对结论的影响。
- 外部标题、新闻和公告文本插入 HTML 时必须转义；不得直接拼接为可执行 HTML 或脚本。
- 一次运行使用唯一 `run_id`，不得只用 `HHMM` 区分；文件名中的代码、名称必须校验并过滤路径字符。
- 所有产物统一登记：类型、路径、状态、生成耗时、大小、失败原因。
- PDF 失败必须进入运行结果；不得仅打印错误后将六件套标为完成。
- 输出状态至少分为 `complete`、`partial`、`failed`，并事先定义必需产物和允许降级的产物。
- 关键 JSON、清单等文件采用临时文件加原子替换；中断后不得留下看似完整的半文件。
- 分开记录分析耗时、渲染耗时和总耗时；总耗时在交付阶段结束后记录。
- 图表导出必须等待明确的渲染就绪信号；超时、脚本加载失败不得误判为完整 PDF。
- 建议固定并本地提供报告所需前端依赖，保证离线查看和导出；相关字体、图表和分页变更须抽样查看实际输出。

## 8. 日志与错误处理

- 日志至少包含 `run_id`、标的、阶段、数据源、状态、耗时、尝试次数和错误码。
- 成功请求数、有效数据数、空结果数、失败数分别统计，禁止只用“未抛异常”计算成功率。
- 优先捕获明确异常；编排边界可捕获 `Exception` 以隔离模块失败，但必须记录原因并返回明确失败状态。
- 禁止 `except: pass` 或捕获异常后无说明返回正常默认值。
- 日志不得输出凭据、令牌、敏感请求头；详细诊断与面向用户的摘要分开。
- 依赖未安装、源不可用、数据为空、解析失败须可区分。

## 9. 测试要求

测试应验证行为和业务约束，不能只复刻实现或检查源码中是否存在某段字符串。

| 类型 | 要求 |
| --- | --- |
| 单元测试 | 核心公式、状态转换、单位转换使用固定输入，默认不联网 |
| 契约测试 | 覆盖四种采集状态、字段类型、口径和错误传播 |
| 集成测试 | 使用可控数据源与临时输出目录验证采集到产物链路 |
| 在线冒烟 | 单独标记并显式运行，记录时间、环境和真实失败原因 |
| 渲染检查 | 影响布局、图表或分页时检查代表性实际产物 |

必须优先补齐以下回归场景：

- 最近支撑/压力选择、候选为空、候选落在错误方向。
- fetcher 返回错误结果时，日志不能标为 `ok`。
- 超时、可恢复错误重试、不可恢复错误不重试。
- 同一分钟两次运行产物不能覆盖。
- PDF 失败导致部分交付，并保留其他成功产物。
- 节假日、开盘前、盘中日线未完成时的新鲜度判断。
- 缺数据时评分和报告按规则降级，多种输出结论一致。

测试不得依赖个人绝对路径或“今天已经跑过报告”。需要产物时由 fixture 在临时目录生成。关键回归测试不得因没有手工产物而跳过。

无需为纯文案或低影响格式调整编写镜像测试；仍需完成与改动相称的检查。

## 10. 配置、依赖与自动检查

- 路径由项目根目录、配置或命令行参数解析，不得硬编码个人桌面路径。
- 超时、限流、输出目录等集中配置；密钥通过环境变量等外部配置注入，不得提交。
- 声明实际支持的 Python 版本，并与类型语法和依赖要求一致。
- 建立项目依赖清单和可复现的锁定方案，区分运行与开发依赖。
- 建议统一使用 Ruff 进行格式和静态检查，pytest 执行测试；核心模型与计算模块逐步纳入类型检查。
- 建立 CI：在声明的 Python 环境安装依赖，执行格式、静态检查及离线核心测试。
- 工具配置尚未落地前，不得将这些检查写为“已通过”；引入后使用统一配置，避免个人标准不同。
- 历史静态问题可登记基线，但本次变更不得新增问题；禁止无理由大范围忽略规则。

## 11. 文档与变更验收清单

README 应说明当前入口、安装方式、支持环境、输出内容和限制。流程图应区分已实现、计划中和降级路径。

每次涉及逻辑或链路的变更按实际适用项检查；不适用项写明原因：

- [ ] 问题、目标行为、输入输出及边界明确。
- [ ] 计算规则与注释、示例一致。
- [ ] 数据类型、单位、时点、复权与范围明确。
- [ ] 空数据、不支持、错误和成功正确区分。
- [ ] 网络请求有超时与总预算，重试及并发受控。
- [ ] 无新增全局 monkey patch、个人路径或敏感信息。
- [ ] 产物与日志完整登记，部分失败没有被掩盖。
- [ ] 相关测试及检查通过，必要时检查实际渲染输出。
- [ ] 文档与流程图反映最终实现。
- [ ] 变更说明写明修改内容、验证结果及尚未解决的限制。

“文件存在”“测试进程退出码为零”“页面可以打开”均不能单独证明业务验收完成。

## 12. 现有项目整改顺序

| 优先级 | 整改事项 | 完成标准 |
| --- | --- | --- |
| P0 | 三价位语义与实现统一 | 规则有例子，边界测试通过，报告描述同步 |
| P0 | 章节失败状态正确传播 | 错误返回不再计为成功，缺失情况进入报告 |
| P1 | PDF 与六件套统一验收 | 全部产物有记录，可识别部分交付，重复运行不覆盖 |
| P1 | 超时、重试与 TLS 处理 | 总预算有效，移除自动关闭证书校验及全局请求替换 |
| P1 | 测试脱离个人环境 | 新环境可运行核心离线测试，无当日报告前置条件 |
| P2 | 模块拆分与契约迁移 | 逐步统一旧 fetcher 与 Registry，主入口只保留编排 |
| P2 | 依赖与 CI 建设 | 安装方式可复现，提交自动执行核心检查 |
| P2 | 文档、流程图和渲染一致性 | 并行、时间盒、产物状态均与代码及验收证据对应 |

本阶段优先修正结果正确性和失败可见性，再做结构整理与展示优化。每项独立验证，避免通过一次大重构混合引入业务变化。
